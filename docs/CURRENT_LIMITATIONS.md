# Current Limitations and Alternatives

This register is a candid snapshot of the launched V0.1 as of 2026-08-22. It combines current
operational gaps, deliberately accepted launch tradeoffs, and product limitations that are easy to
miss when reading milestone documents separately. A limitation here is not automatically a bug or
a launch blocker: Gate F was approved with the listed tradeoffs. The alternatives are available
directions or existing fallbacks, not an approved implementation roadmap.

Use the Product Decision Chronicle for product intent, the ADRs for accepted architectural
decisions, and the Runbook for exact operations. Update this register when a limitation is removed,
materially changes, or becomes an incident.

Status meanings:

- **Active gap** — the desired behavior or operating control is not fully present today.
- **Pending operation** — code exists, but a time-sensitive human operation still remains.
- **Accepted tradeoff** — intentionally accepted for the low-cost small-community launch.
- **Deliberate scope** — intentionally outside V0.1 rather than accidentally missing.

## Hosting, recovery, and operations

| Status            | Current drawback or constraint                                                                                                                                                                                                                                                                                                                 | Practical impact                                                                                                                                                                                                    | Current fallback or alternative                                                                                                                                                                                                                                                                                                             |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Accepted tradeoff | **The public site uses the Railway-generated domain directly.** Cloudflare cannot proxy the Owner's `*.up.railway.app` host because the parent domain belongs to Railway. There is no custom domain, Cloudflare WAF, edge bot shield, or Cloudflare rate limit in front of the app.                                                            | Railway provides the current hosting/network boundary, but a large Layer-7 attack could affect availability or cost before the in-process controls respond. The generated URL is also a weaker long-term brand.     | Keep application CSRF guards, security headers, PostgreSQL quota/risk truth, limits, logs, and spend alerts. If a measured trigger occurs, buy/use an Owner-controlled domain, compare Cloudflare proxy-on with DNS-only, and explicitly decide whether the direct Railway origin remains reachable. See ADR 0005.                          |
| Accepted tradeoff | **Web and PostgreSQL are single-region, single-service resources on Railway Hobby.** Web has one Singapore replica; there is one production database and no application-managed failover, read replica, or multi-region path.                                                                                                                  | A regional/provider/database incident can make the whole product unavailable. The current process-local limiters and cache do not coordinate across future replicas and reset on deployment.                        | Use Railway health/restart behavior and the documented incident freeze/restore path today. Add distributed limits/cache, more replicas, a stronger database plan, or provider redundancy only when traffic and recovery requirements justify them.                                                                                          |
| Accepted tradeoff | **There is no managed volume backup or point-in-time recovery.** Daily logical dumps target an RPO of 24 hours and an operator-driven RTO of four hours. Restores are manual and must use a separate empty database. Dumps rely on private R2/provider encryption at rest and HTTPS in transit; they are not client-side/passphrase encrypted. | A recovery can lose changes since the latest successful dump and requires an operator. Fine-grained recovery to an arbitrary moment is unavailable.                                                                 | Railway's daily `backup-production` job creates and verifies the private R2 copy without the Owner's Mac. The Mac command is a fallback, and a separate restore drill is required monthly and after material schema changes. Upgrade to managed PITR/volume backups or add client-side encryption if the recovery/security targets tighten. |
| Active gap        | **Backup retention policy is documented but not automated.** ADR 0004 calls for seven daily and four weekly recovery points, but the current uploader only creates/verifies dated R2 objects; it neither promotes weekly copies nor deletes old ones.                                                                                          | Backups currently accumulate indefinitely unless R2 lifecycle settings or an operator remove them. This is inexpensive at today's size but does not prove the stated retention policy is enforced.                  | Until automation exists, review R2 and retain/delete copies manually or configure a carefully tested bucket lifecycle. A future pruning job should protect the newest verified recovery points and refuse broad deletion.                                                                                                                   |
| Accepted tradeoff | **Restore verification is periodic, not part of every hosted backup.** The daily job verifies dump metadata and remote object size/checksum, but it cannot restore into its ephemeral container as proof that PostgreSQL can replay the archive.                                                                                               | A successful daily upload is strong copy-integrity evidence, not a daily full restore test.                                                                                                                         | Run the guarded scratch-database restore at least monthly and after schema changes, then record duration/counts. A later isolated recovery service could automate restore drills if the extra resources are justified.                                                                                                                      |
| Accepted tradeoff | **Operations visibility is provider-native and lightweight.** V0.1 has structured Railway logs, daily KPI/integrity jobs, failed-job email, spend controls, and a Cloudflare billing alert, but no Sentry/APM/on-call system or R2 usage panel in Admin. The failed-deployment and spend-threshold email paths were not deliberately forced.   | Error grouping, traces, cross-service correlation, and proactive R2 capacity reporting require manual dashboard/log inspection. An unobserved notification-path problem may be discovered only during a real event. | Continue Railway/Cloudflare dashboards, alerts, KPI and integrity review. Add external error tracking or a private Admin operations panel later, without making it a public-request or Mainland-China dependency.                                                                                                                           |
| Accepted tradeoff | **Every Railway service is connected to the same repository.** Web and the scheduled services build from repository commits; no config contains path-based watch filters. The backup job has a separate image, while most other jobs share the Web image.                                                                                      | A documentation-only or unrelated commit may trigger multiple builds/deployments, consuming build slots and small amounts of time/compute.                                                                          | Accept the simplicity at current cost. Later add verified watch paths, publish/reuse a prebuilt image, or split operational jobs only if build churn becomes material.                                                                                                                                                                      |
| Accepted tradeoff | **Capacity evidence is intentionally small.** The recorded staging load was 50 fresh-visitor scenarios at concurrency 5, and the launch review observed only a small seven-day beta sample.                                                                                                                                                    | This proves the tested path and integrity behavior, not capacity for tens of thousands of daily users, sustained attacks, or peak concurrency. Cost and latency at that scale remain unknown.                       | Increase load tests gradually while watching Web/DB CPU, memory, connections, latency, errors, egress, and spend. Scale based on measured bottlenecks rather than the current sample.                                                                                                                                                       |
| Active gap        | **Mainland China route coverage is incomplete.** China Mobile 4G/Wi-Fi worked, but China Telecom and China Unicom were not tested, and no separately classified China Mobile evening-peak window was recorded.                                                                                                                                 | Accessibility and latency cannot be generalized to all three carriers or peak periods. Missing evidence is not a route failure.                                                                                     | Retest from real Telecom/Unicom devices when available. If measurements justify it, reopen the custom-domain/Cloudflare A/B decision rather than assuming it improves Mainland routing.                                                                                                                                                     |
| Accepted tradeoff | **The application and primary database share Railway as one failure domain.** R2 is an independent database-backup destination, but it does not run the site or provide a hot standby.                                                                                                                                                         | A Railway outage still takes the live product offline even though the data has a second provider copy.                                                                                                              | Restore the newest safe R2 dump to a sibling/alternate database and redeploy according to the Runbook. A warm standby or second hosting provider is a later availability option, not present today.                                                                                                                                         |

## Security, identity, and public policy

| Status            | Current drawback or constraint                                                                                                                                                                                                                        | Practical impact                                                                                                                                                                        | Current fallback or alternative                                                                                                                                                                                                                                         |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Accepted tradeoff | **Risk scoring remains in `observe` mode.** Suspicious signals are recorded for review, but otherwise valid votes continue to count until enforcement is deliberately enabled; infrastructure limits and the 150 full-weight daily quota still apply. | This minimizes false positives on shared Mainland networks but provides less automatic anti-abuse blocking during the initial beta.                                                     | Review real reason-code/KPI evidence, revoke proven bad Votes through Admin, tune thresholds, and switch selected rules to `enforce` only with explicit Owner approval. Cloudflare or a distributed limiter is a later defense-in-depth option.                         |
| Accepted tradeoff | **Public identity is a browser cookie, not an account.** Clearing cookies, changing browsers/devices, or losing the cookie creates a new visitor. The daily privacy-preserving IP risk key is only a secondary signal and expires.                    | Votes cannot be recovered or linked across devices, and a determined user can obtain more than one anonymous identity.                                                                  | Keep the low-friction anonymous model for V0.1. Accounts, Steam login, device attestation, or stronger network controls are alternatives if abuse or cross-device continuity becomes important.                                                                         |
| Accepted tradeoff | **Admin authentication is deliberately minimal.** There is no web registration, email/password reset, MFA, SSO, or role-based permission model; accounts are created from a trusted CLI and the current operation model is one Owner.                 | Losing the password requires trusted-host recovery, and compromise of that credential/session has broad administrative impact.                                                          | Protect Railway/GitHub/Cloudflare accounts with their provider MFA, keep the Admin password unique, revoke sessions/deactivate accounts in the database path, and create/rotate Admin access through the trusted CLI. Add application MFA/roles if more operators join. |
| Accepted tradeoff | **There is no public privacy/contact page or dedicated contact email.** The Owner explicitly removed it for the small community beta while the site still uses an anonymous cookie, short-lived IP-risk HMACs, and first-party metrics.               | Users have no on-site policy, data explanation, or takedown/contact channel. This becomes harder to justify with broader reach, a custom domain, outside contributors, or monetization. | Continue data minimization and 90-day cleanup now. Publish a suitable privacy/contact surface when the agreed growth trigger occurs; do not infer that the current absence resolves legal obligations in every jurisdiction.                                            |
| Active gap        | **The repository has no selected software license.** `README.md` still says “To be determined.”                                                                                                                                                       | Public source visibility does not by itself grant clear reuse, modification, redistribution, or contribution terms.                                                                     | Select and add an explicit license before inviting outside reuse/contributions or treating the repository as open source. Keep third-party asset rights separate from the code license.                                                                                 |
| Deliberate scope  | **Daily full-weight quota state is hidden in the public UI.** After 150 Ballots, actions are durably stored as `THROTTLED` and do not affect rankings, but the UI does not show remaining quota or a distinct throttled result.                       | A highly active user may believe later choices influenced the ranking when they did not. The design avoids exposing a precise anti-abuse boundary but costs transparency.               | Keep the backend response/audit truth and current anti-gaming choice. Alternatives include stopping new Ballots, showing a generic daily-limit message, or disclosing non-counting status after resolution; each requires a product decision.                           |
| Deliberate scope  | **Manual reload is treated as Skip.** Reloading an unresolved Vote consumes that opportunity, records normal Skip counters, and requests a new pair.                                                                                                  | An accidental reload has a durable, non-scoring effect and advances the daily ordinal.                                                                                                  | The current UI makes retries idempotent and distinguishes a real browser reload from rendering. Alternatives are preserving the same pair or adding an explicit replace action, but ADR 0003 records why those were not selected.                                       |

## Product model and engineering coverage

| Status            | Current drawback or constraint                                                                                                                                                                                                                                                                                                 | Practical impact                                                                                                                                                                               | Current fallback or alternative                                                                                                                                                                                                                             |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Deliberate scope  | **The annual ranking is a simple cumulative `+1/-1/0` model over uniformly random pairs.** It has no Elo/Bradley–Terry strength model, exposure normalization, required minimum sample, recency weighting, or confidence interval. New players start at zero.                                                                  | Scores reflect community pairwise activity, matchup luck, sample size, and time in the Pool as well as preference. They must not be presented as an objective skill rating.                    | Preserve zero-sum integrity, public win/loss/Skip/H2H context, random pairing, and honest small-sample messaging. More sophisticated ratings or exposure controls are alternatives for a future Edition and require an explicit product/migration decision. |
| Deliberate scope  | **Active and approved retired Special Players share the same random pairing pool.** Their data is frozen and their inclusion is an Owner community decision, not current-roster evidence.                                                                                                                                      | They can influence present rankings while not being directly comparable on current form or fresh HLTV metrics.                                                                                 | Keep the explicit `SPECIAL` reason and retired label, disable pairing without deleting history, or create a separate mode/Edition if the community later wants current-only rankings.                                                                       |
| Deliberate scope  | **The public product is Chinese-first and has no localization system.**                                                                                                                                                                                                                                                        | Non-Chinese users and future translators do not have a supported language switch or extraction workflow.                                                                                       | Keep one coherent language for the current audience. Add an i18n/message layer and translated metadata only if audience evidence justifies it.                                                                                                              |
| Deliberate scope  | **Public “online now” and “daily users” counters are not shown.** Existing `product_event` and `anonymous_visitor.last_seen_at` only cover cookied visitors (usually after the first Ballot) and have no heartbeat; KPI daily visitors are Ballot issuers. Investigated 2026-08-24, not implemented.                          | The site cannot honestly display current or daily headcount from stored rows without undercounting lurkers or inventing presence.                                                              | Keep first-party KPI/admin evidence. A later heartbeat plus Shanghai-day distinct `visitor_id` could support a labeled counter; see `docs/OPEN_QUESTIONS.md`. Do not add third-party analytics or IP-based people counts.                                    |
| Active gap        | **Automated browser coverage is Chromium-only and is not run by GitHub CI.** Playwright defines desktop Chrome and Pixel 7 emulation; Firefox, WebKit/Safari, and real-device behavior are not automated. CI currently runs lint, formatting, types, unit/integration tests, migrations, and build, but omits `pnpm test:e2e`. | Browser regressions can pass CI, and mobile emulation is not equivalent to real iOS Safari or a broad desktop matrix. Gate F's manual/browser evidence is a point-in-time check.               | Run the six E2E journeys before significant releases, add them to CI when runtime is acceptable, and expand to WebKit/Firefox or targeted real-device checks as usage warrants.                                                                             |
| Accepted tradeoff | **CI never contacts live providers and does not perform a real backup/restore or production smoke.**                                                                                                                                                                                                                           | It cannot detect provider blocking/markup changes, Railway configuration drift, broken credentials, or recovery failures. Running those checks on every commit would also be unsafe and flaky. | Keep deterministic fixtures in CI; use scheduled jobs, deployment smoke, failure alerts, monthly restore drills, and guarded local capture as the operational verification layer.                                                                           |

## Current facts that are not missing work

These are sometimes confused with limitations but are already implemented:

- M10 and Gate F are complete; the real `2026 Beta Edition` is active.
- Production contains 92 pairing-enabled Players: 70 Core, 20 Review Manual, and two retired
  Specials. Current reviewed stats were imported for all 90 non-retired Pool Players; unsupported
  fields remain intentionally absent.
- Current Player portraits and Team logos are local public files. PostgreSQL stores their paths,
  while R2 stores private logical database backups rather than the website's media.
- Daily production backup creation/upload no longer depends on the Owner's Mac. The Mac is only the
  manual fallback and monthly restore-drill workstation.
- “Automatic” Candidate Pool evaluation means deterministic evidence evaluation and proposal
  creation. It has never meant automatic live admission; Owner/Admin approval is a permanent Gate D
  safety boundary unless a later decision explicitly changes it.
