# Database Model and Operations

## Schema status

The complete V0.1 PostgreSQL model is implemented in:

- `src/db/schema/enums.ts`
- `src/db/schema/tables.ts`
- `drizzle/0000_m1_initial_schema.sql`
- `drizzle/0001_m8_integrity_hardening.sql`
- `drizzle/0002_m8_risk_key_constraints.sql`

The initial migration creates 27 tables and 21 PostgreSQL enums. M8 adds `risk_observation`,
`api_request_metric`, and persisted Ballot risk reasons through an ordered forward migration. The
migrations are generated from the Drizzle schema, committed for review, and tested against an empty
PostgreSQL 18 database.

## Conventions

- PostgreSQL is the only application database.
- Timestamps are `timestamptz` and represent UTC instants.
- Business quota dates are PostgreSQL `date` values computed in `Asia/Shanghai` when a Ballot is
  issued.
- High-volume internal identifiers are `bigint generated always as identity`; Drizzle maps them to
  JavaScript `bigint` to avoid precision loss.
- Public Ballot identifiers are random UUIDs generated by PostgreSQL.
- Slugs are the public identifiers for teams and players.
- Historical, audit, and domain foreign keys use `ON DELETE RESTRICT`. V0.1 disables or archives
  records rather than deleting them.
- Every counter is non-negative at the database layer.
- JSON columns that represent arrays or objects have matching `jsonb_typeof` checks.

## Database-enforced invariants

The migration SQL is the final enforcement layer for row-local and uniqueness rules.

| Invariant                                                                   | Constraint/index                                                  |
| --------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| At most one active Edition                                                  | `edition_single_active` partial unique index                      |
| At most one current roster row per player                                   | `roster_one_current_per_player` partial unique index              |
| At most one open Ballot per visitor and Edition                             | `ballot_one_open_per_visitor_edition` partial unique index        |
| At most one Vote per Ballot                                                 | `vote_ballot_unique`                                              |
| Ballot pair is canonical and its orientation matches                        | `ballot_canonical_pair`, `ballot_orientation_matches_pair`        |
| Ballot status, resolution, and timestamp agree                              | `ballot_resolution_state`                                         |
| Vote choice agrees with winner/loser nullability                            | `vote_choice_player_shape`                                        |
| Revoked Vote has complete audit fields                                      | `vote_revocation_state`                                           |
| Ranking score equals wins minus losses                                      | `player_ranking_score_matches_record`                             |
| PairAggregate is canonical and counted values do not exceed observed values | `pair_aggregate_canonical_pair`, `pair_counted_*_within_observed` |
| Pool player source and pairing state are structurally valid                 | `pool_player_source_shape`, `pool_player_pairing_state`           |
| Import approval/rejection state has matching review/application fields      | `pending_import_review_state`                                     |
| Sync run status agrees with completion timestamp                            | `sync_run_lifecycle`                                              |

Additional checks cover date ordering, positive ranks and TTL values, nonblank required text, event
approval shape, session lifetimes, JSON shape, and all counters.

## Service-enforced invariants

PostgreSQL `CHECK` constraints cannot safely query other rows or tables. The following rules remain
service responsibilities and require integration coverage when those services are implemented:

- a team-derived Pool player uses the same admission type and Edition as its source team entry;
- Vote Edition, visitor, winner, and loser agree with the referenced Ballot orientation;
- Edition status transitions expire open Ballots atomically;
- a Ballot is issued only for the currently active Edition and two currently active Pool entries;
- the sum of all player scores in an Edition remains zero; M4 enforces this transactionally and
  provides `pnpm score:check -- --edition <code>` for cross-table verification;
- admin/session activity and expiration are evaluated at authentication time;
- pending import approval revalidates source freshness and current state before applying changes.

## Commands

The commands read `.env`; `DATABASE_URL` selects the target database.

```bash
pnpm db:generate  # generate a migration after a reviewed schema change
pnpm db:check     # verify migration journal consistency
pnpm db:migrate   # apply committed migrations
pnpm db:seed      # apply repeatable development-only sample data
pnpm test:integration
```

Migration generation never replaces SQL review. Inspect enum values, nullability, defaults,
identity modes, foreign-key actions, checks, and partial indexes before committing a migration.

## Schema evolution policy

The V0.1 schema is a reviewed starting point, not a frozen final design. New product requirements,
operational learning, and data-source changes are expected to produce later schema revisions.

- Change the Drizzle schema first, then add a new ordered migration; do not rewrite a migration that
  may already have been applied outside an expendable local database.
- Review compatibility, backfill, index-build, locking, and rollback implications for every change.
- Prefer staged changes for populated systems: add compatible structure, backfill and deploy code,
  then tighten constraints or remove obsolete structure in a later migration.
- Record material product or invariant changes in the Product Decision Chronicle and add or amend an
  ADR when the architectural boundary changes.
- Extend integration coverage with each migration so both an empty build and an upgrade from the
  previous committed schema remain trustworthy.

## Integration-test database lifecycle

`tests/integration/helpers/database.ts` manages one fixed database named `csr_integration_test` on
the server selected by `DATABASE_URL`:

1. Drop only `csr_integration_test` if it exists.
2. Create it from `template0`.
3. Apply every committed migration from `drizzle/`.
4. Run constraint tests without mocking PostgreSQL.
5. Close all test connections and drop only `csr_integration_test`.

The lifecycle never drops the database named in `DATABASE_URL`.

## Development seed

`pnpm db:seed` inserts an explicitly fictional dataset:

- one development Edition, activated only when no other Edition is active;
- two sample teams and four sample players;
- current rosters, Pool entries, zeroed ranking rows, and one sample event;
- one disabled seed admin used only to satisfy approval foreign keys.

The seed account has no usable password hash. The seed is transactional, repeatable, and must not
run when `NODE_ENV=production`. It is illustrative test data, not the launch Candidate Pool.

## Current implementation boundaries

- M4 implements locked Vote resolution, ranking and PairAggregate mutation, audited service-level
  revocation, and cross-table score integrity reporting without changing the M1 schema.
- Vote revocation deliberately preserves observed aggregate and usage history while reversing only
  counted ranking effects. See `docs/VOTE_RESOLUTION.md`.
- No migration rollback is generated automatically; before production data exists, a failed local
  migration is tested by rebuilding an empty database.
- PostgreSQL extensions are not required by the initial schema.
- M8 persists only date-rotating 32-byte IP HMAC keys, bounded reason codes, and API timing/status
  metrics. Raw IP addresses have no schema column. Retention nulls old Ballot/Vote keys and either
  nulls or removes old risk observations while preserving Vote/ranking history.
